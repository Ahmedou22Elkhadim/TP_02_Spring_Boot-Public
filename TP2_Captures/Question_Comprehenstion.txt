# Réponses aux questions de compréhension

---

## 1. Différence entre IoC et DI — et inversion du contrôle

**IoC (Inversion of Control)** est un **principe d'architecture** : c'est un conteneur externe (le Spring IoC Container / `ApplicationContext`) qui prend en charge la création des objets, l'assemblage de leurs dépendances et leur cycle de vie. Le code applicatif ne décide plus *quand* ni *comment* les objets sont créés.

**DI (Dependency Injection)** est le **mécanisme concret** par lequel ce principe se réalise : Spring fournit (« injecte ») les dépendances à un bean, via le constructeur, un setter ou un champ.

**Inversion du contrôle par rapport à `new CricketCoach()`** :
Avec `new CricketCoach()`, c'est *votre* code qui :
- décide de la classe concrète à instancier (couplage fort),
- choisit le moment de la création,
- gère le cycle de vie (et oublie souvent de libérer les ressources).

Avec Spring, c'est le **conteneur** qui décide *quelle* implémentation de `Coach` créer, *quand* la créer (eager/lazy), *à qui* la fournir, et *quand* la détruire. Votre contrôleur se contente de **déclarer un besoin** (`Coach theCoach`) ; il ne sait plus *comment* l'objet est construit. Le contrôle est donc **inversé** : il passe du code métier vers le conteneur.

**Bénéfices** : couplage faible (le contrôleur dépend de l'abstraction `Coach`), code testable (on peut injecter un mock), configuration centralisée, cycle de vie géré automatiquement.

---

## 2. Pourquoi l'injection par constructeur est recommandée

Trois arguments principaux (au moins deux demandés) :

1. **Immuabilité et objet toujours valide** : les dépendances peuvent être `final`, assignées une seule fois dans le constructeur. L'objet est **toujours dans un état cohérent** dès qu'il existe — impossible de créer un `DemoController` sans `Coach`. Avec l'injection par champ, l'objet peut exister dans un état partiellement initialisé.

2. **Testabilité** : on instancie la classe directement avec des mocks, sans réflexion ni conteneur Spring :
   ```java
   new DemoController(mockCoach);   // test unitaire pur
   ```
   Avec l'injection par champ (`@Autowired private Coach coach;`), il faut un runner Spring ou de la réflexion pour injecter le mock → tests plus lourds et plus lents.

3. **Détection précoce des erreurs** : si une dépendance obligatoire manque, l'application **échoue au démarrage** (`NoSuchBeanDefinitionException`) plutôt qu'à l'exécution (`NullPointerException`). Les cycles de dépendances sont aussi détectés au démarrage.

4. (Bonus) **Visibilité des dépendances** : le constructeur **déclare explicitement** toutes les dépendances. L'injection par champ les cache dans la classe, ce qui rend le couplage invisible et favorise les classes « fourre-tout » avec trop de dépendances.

5. (Bonus) **Pas de dépendance à Spring dans le code métier** : la classe reste un POJO, utilisable hors conteneur.

## 3. `NoUniqueBeanDefinitionException` : situation, résolution, priorité

**Situation** : elle survient quand **plusieurs beans** du même type sont candidats à l'injection et que Spring ne peut pas choisir. Exemple classique du TP : 4 implémentations de `Coach` (`BaseballCoach`, `CricketCoach`, `TennisCoach`, `TrackCoach`) toutes `@Component`, et un contrôleur qui demande simplement `Coach theCoach`.

**Deux façons de la résoudre** :

1. **`@Qualifier("id")`** sur le point d'injection → désigne **explicitement** le bean voulu :
   ```java
   public DemoController(@Qualifier("cricketCoach") Coach theCoach) { ... }
   ```

2. **`@Primary`** sur l'une des classes candidates → désigne le **choix par défaut** quand aucun `@Qualifier` n'est présent :
   ```java
   @Component
   @Primary
   public class TrackCoach implements Coach { ... }
   ```

**Priorité si les deux sont présents** : **`@Qualifier` gagne sur `@Primary`**. Vérifié dans le TP : avec `@Primary` sur `TrackCoach` **et** `@Qualifier("cricketCoach")` sur le constructeur, c'est `CricketCoach` qui est injecté. Règle : *`@Qualifier` est explicite, `@Primary` est un défaut ; l'explicite l'emporte toujours.*

**Piège** : mettre `@Primary` sur **deux** beans du même type → `NoUniqueBeanDefinitionException: more than one 'primary' bean found`. Un seul `@Primary` par type.

## 4. Id par défaut d'un bean — et comment le forcer

**Id par défaut** :
- Pour un bean issu de **component scanning** (`@Component`, `@Service`, etc.) : c'est le **nom simple de la classe avec la première lettre en minuscule**. Exemple : `CricketCoach` → `cricketCoach`, `SwimCoach` → `swimCoach`.
- Pour un bean déclaré via **`@Bean`** : c'est le **nom de la méthode** qui produit le bean. Exemple : `@Bean public Coach swimCoach()` → id `swimCoach`.

**Forçage manuel** :
- Sur un `@Component` : `@Component("monCoach")` (ou `@Service("monCoach")`, etc.).
- Sur un `@Bean` : `@Bean("aquatic")` (ou `@Bean(name = "aquatic")`).

L'id forcé est celui qu'on utilise ensuite dans `@Qualifier("...")`.

## 5. `@Lazy` : avantages, inconvénients, « à utiliser avec parcimonie »

**Avantages** :
- **Démarrage plus rapide** : les beans non utilisés au démarrage ne sont pas créés.
- **Économie mémoire** : les beans jamais utilisés ne sont jamais instanciés (utile pour des beans coûteux ou conditionnels).
- **Développement plus fluide** : on peut démarrer rapidement une app dont une partie seulement est en cours de test.

**Inconvénient majeur** :
- Les **erreurs de configuration** (dépendance manquante, `@Qualifier` invalide, ambiguïté, échec d'un `@PostConstruct`, exception dans le constructeur…) ne sont **détectées qu'à l'exécution**, au moment où le bean est effectivement demandé — parfois longtemps après le démarrage, sur une route rarement appelée. Sur une application en production, un bug peut donc rester **caché** jusqu'au pire moment.
- **Comportement moins prévisible** : l'ordre et le moment de création des beans deviennent plus difficiles à raisonner (utile de savoir qu'un `@Lazy` sur un singleton n'a d'effet qu'au premier accès ; sur un prototype, il n'a aucun effet puisque le bean est de toute façon créé à chaque demande).

**« À utiliser avec parcimonie »** : parce que le gain (démarrage/mémoire) est souvent marginal comparé au risque de masquer des erreurs de câblage. On réserve `@Lazy` (ou le mode global `spring.main.lazy-initialization=true`) aux cas où le démarrage est réellement problématique, et **jamais** en production sans tests d'intégration complets qui exercent tous les beans.

## 6. `/check` passe de `true` à `false` : qu'a-t-on changé, et qu'est-ce que cela prouve ?

**Ce qui a été changé** : on a fait passer `CricketCoach` du scope **`singleton`** (défaut) au scope **`prototype`** :
```java
@Component
@Scope(ConfigurableBeanFactory.SCOPE_PROTOTYPE)
public class CricketCoach implements Coach { ... }
```
Le contrôleur, lui, reste inchangé : il reçoit **deux fois** le même coach via `@Qualifier("cricketCoach")` et compare les références avec `==` :
```java
@GetMapping("/check")
public String check() {
    return "Comparing beans: myCoach == anotherCoach, " + (myCoach == anotherCoach);
}
```

**Ce que cela prouve** :
- **`singleton` (résultat `true`)** : Spring crée **une seule** instance et la **partage** entre toutes les demandes. Les deux paramètres du constructeur pointent vers le **même objet** en mémoire → `==` renvoie `true`. On a aussi observé **une seule** trace `In constructor:` au démarrage.
- **`prototype` (résultat `false`)** : Spring crée une **nouvelle instance** à **chaque demande**. Les deux injections reçoivent **deux objets distincts** → `==` renvoie `false`. On a observé **deux** traces `In constructor:`.

Cela prouve donc directement que la **portée du bean** contrôle le **nombre d'instances** créées et **partagées** par le conteneur : `==` compare les références, pas le contenu — c'est exactement le test qui distingue les deux scopes.

## 7. Cycle de vie d'un bean singleton — et `@PreDestroy` en prototype

**Ordre exact pour un singleton** :

```
1. Instanciation (constructeur)
2. Injection des dépendances (constructeur / setter / champ)
3. Appel de la méthode @PostConstruct
4. ... utilisation du bean (endpoints, appels métier, etc.) ...
5. Appel de la méthode @PreDestroy
6. Destruction (fermeture du contexte Spring, arrêt propre de l'application)
```

Observé dans le TP : au démarrage, `In constructor: CricketCoach` **puis** `In doMyStartupStuff()` ; à l'arrêt propre (`Ctrl+C` ou bouton Stop), `In doMyCleanupStuff()`.

**Pourquoi `@PreDestroy` n'est pas appelé pour un `prototype`** :
Spring ne **conserve aucune référence** aux beans `prototype` après les avoir remis à l'appelant. Il ne peut donc pas savoir quand le client a fini de les utiliser, ni quand déclencher leur destruction. Plutôt que de risquer des destructions prématurées ou des fuites mémoire, Spring **abandonne la gestion de la fin de vie** de ces beans : la destruction est **à la charge du code client** (qui a reçu l'instance). En revanche, `@PostConstruct` **est** appelé, car Spring contrôle toujours la **création** de chaque instance, même s'il ne la garde pas.

Vérifié dans le TP : en `prototype`, on voit `In constructor:` + `In doMyStartupStuff()` à chaque injection, mais **aucune** trace `In doMyCleanupStuff()` à l'arrêt.

## 8. Trois cas où préférer `@Bean` (dans une `@Configuration`) à `@Component`

1. **Classe externe non modifiable** : vous voulez injecter une instance d'une classe d'une librairie tierce (ex. `RestClient`, `ObjectMapper`, `DataSource` d'un driver JDBC) sur laquelle vous **ne pouvez pas** ajouter `@Component`. Vous déclarez alors un `@Bean` dans **votre** classe `@Configuration`.

2. **Création complexe / factory** : la construction nécessite du code qui ne tient pas dans un constructeur — builder, valeurs calculées à partir de propriétés, configuration conditionnelle (`@ConditionalOnProperty`), appel à une API externe, gestion d'exceptions, choix d'implémentation selon l'environnement. Exemple :
   ```java
   @Bean
   public DataSource dataSource() {
       return DataSourceBuilder.create()
           .url(env.getProperty("db.url"))
           .username(env.getProperty("db.user"))
           .build();
   }
   ```

3. **Plusieurs instances du même type avec configurations différentes** : `@Component` ne produit qu'**une** instance par classe. `@Bean` permet de déclarer **plusieurs méthodes** produisant **plusieurs beans distincts** du même type, chacun avec son id et sa configuration, injectables via `@Qualifier`. Exemples : deux `RestClient` pour deux APIs, deux `DataSource` (lecture/écriture), plusieurs `Coach` paramétrés différemment.

**En résumé** : `@Component` pour **vos** classes à création simple ; `@Bean` pour les **classes tierces**, les **créations complexes**, et les **multi-instances** d'un même type.
